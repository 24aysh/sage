# Sage V1.0 As-Built and Release Specification

## Document status

> **Status:** Historical as-built and release record. Retained for design
> history; use [`../docs/architecture.md`](../docs/architecture.md) for current
> behavior.

This document records the V1.0 system that exists on
`feat/v1-github-native` as of 2026-08-22. It is the as-built counterpart to
[`08_V1.0_design.md`](08_V1.0_design.md), the implementation plan in
[`09_V1.0_implementation_plan.md`](09_V1.0_implementation_plan.md), and the
operator guide in [`10_V1.0_testing.md`](10_V1.0_testing.md).

The primary live acceptance path has passed: an authorized Issue command ran
Sage and produced a correct draft Pull Request. This document covers backend,
controller, sandbox, workflow, and release behavior only. The landing page is
not part of this specification.

## 1. Release outcome

V1.0 migrates Sage from a local-only issue solver to a GitHub-native
Issue-to-draft-PR workflow without replacing the V0.1 coding core. A maintainer
can post either exact command on a standalone Issue:

```text
/sage solve
/sage fix
```

Both commands have the same semantic result. Sage authorizes the commenter,
records an exact default-branch commit, assembles bounded Issue context, runs
the existing LangGraph solver in an isolated checkout, validates the resulting
Git candidate, creates `sage/issue-<number>`, and opens a draft Pull Request for
human review.

The feature branch is ready for manual review and merge. Sage does not merge
this branch, its generated draft Pull Requests, or any target default branch.

## 2. V1.0 goals covered

| Design goal | Delivered behavior | Primary ownership |
| --- | --- | --- |
| GitHub-native invocation | Exact `/sage solve` and `/sage fix` Issue comments | `commands.py`, `events.py`, workflow filter |
| No maintainer-side clone or `issue.md` | GitHub Actions supplies event and checkout; controller materializes bounded task input | `context.py`, composite actions |
| Isolated real repository | Exact-SHA checkout plus a fresh Docker sandbox per solve | `workspace.py`, `docker.py`, `sage-solve` action |
| Serverless execution | `issue_comment.created` starts hosted GitHub Actions jobs | `.github/workflows/sage.yml` |
| Existing solver reuse | V0.1 `solve_issue` and `LangGraphRuntime` remain the coding engine | `workflow/solve.py`, `runtimes/langgraph/` |
| Maintainer authorization | Current GitHub `write` or `admin` permission is required and rechecked | `authorization.py`, `gate.py`, `workflow/github_issue.py` |
| Exact revision | Gate records a validated SHA; solve verifies the checkout still matches it | `events.py`, `provenance.py`, `workflow/github_issue.py` |
| Deterministic publication | Fixed branch, creation-only push, draft PR, no default-branch push | `publishing.py` |
| Issue feedback | One bot-owned status moves accepted -> working -> terminal | `status.py` and finalizer |
| Safe failure | Bounded categories, artifact allowlist, sandbox cleanup, orphan recovery | `errors.py`, `provenance.py`, `status.py` |
| Run isolation | Per-run checkout, artifact directory, container, and Issue concurrency group | workspace, sandbox, workflow |
| Minimal operations | Standard hosted Actions; no app server, database, queue, or polling process | composite actions and workflow |
| Human control | Draft PR only; no approval, ready-for-review, merge, or auto-merge | publisher and workflow permissions |

## 3. Implemented execution flow

```text
new standalone Issue comment
        |
        v
exact command/event validation
        |
        v
model-free gate: permission + duplicate checks + exact base SHA
        |
        v
accepted Issue status
        |
        v
separate solve job: reauthorize + exact credential-free checkout
        |
        v
bounded Issue context outside target checkout
        |
        v
existing LangGraph runtime + repository tools
        |
        v
network-disabled Docker sandbox
        |
        v
authoritative diff/path/whitespace validation
        |
        v
creation-only sage/issue-<number> push + draft PR
        |
        v
terminal Issue status + allowlisted diagnostics
```

The finalizer runs even when the solve job is interrupted. It preserves an
existing terminal state, links a uniquely reconciled Pull Request, or changes a
still-working invocation to a safe failure state.

## 4. Relevant implementation contracts

Only the code that defines the release-critical contracts is included here.
Production code remains authoritative.

### 4.1 Exact command parsing

```python
_COMMANDS = {
    "/sage solve": SageCommand.SOLVE,
    "/sage fix": SageCommand.SOLVE,
}


def parse_command(body: str) -> SageCommand | None:
    return _COMMANDS.get(body)
```

Whitespace variants, surrounding prose, Pull Request comments, Issue-body
text, and unsupported event payloads do not start a solve.

### 4.2 Authorization and branch ownership

```python
_AUTHORIZED_PERMISSIONS = frozenset({"admin", "write"})


def is_authorized_permission(permission: str) -> bool:
    return permission in _AUTHORIZED_PERMISSIONS


def issue_branch_name(issue_number: int) -> str:
    if issue_number < 1:
        raise ValueError("Issue number must be positive.")
    return f"sage/issue-{issue_number}"
```

The gate and solve job both check permission and remote branch/PR ownership.
An existing Sage branch is never overwritten, and an open matching Pull Request
prevents duplicate model-backed work.

### 4.3 Project model default

```python
DEFAULT_OPENAI_MODEL = "gpt-5.4-mini"


class Settings(BaseModel):
    openai_api_key: str = Field(repr=False)
    openai_model: str = DEFAULT_OPENAI_MODEL
```

The environment loader, `.env.example`, `make first-run`, tracked GitHub
workflow, README, and testing guides use the same default. `OPENAI_MODEL` may
override it deliberately, but no override is required for the supported path.
The previous Codex model name is not a Sage default.

The workflow carries the same fallback:

```yaml
env:
  OPENAI_MODEL: ${{ vars.OPENAI_MODEL || 'gpt-5.4-mini' }}
```

At runtime Sage logs the selected model and only a safe credential state. It
does not log the key, a key substring, or a fingerprint. OpenAI SDK retries are
bounded by `OPENAI_MAX_RETRIES`, which defaults to `2` and accepts `0..10`.

### 4.4 Existing solve core reuse

```python
try:
    sandbox.start()
    repository = build_repository(prepared, sandbox, effective_settings)
    final_output = await runtime.solve(issue_text=issue_text, context=context)
    result = SolveResult(
        run_id=prepared.run_id,
        base_sha=prepared.base_sha,
        summary=final_output.summary,
        remaining_uncertainty=final_output.remaining_uncertainty,
        diff=repository.get_complete_diff(),
        changed_files=repository.get_changed_files(),
        run_dir=prepared.run_dir,
        workspace_dir=prepared.workspace_dir,
    )
    store.persist_result(final_output=final_output, result=result)
    return result
finally:
    sandbox.stop()
```

The shortened excerpt highlights the ownership contract. Git, not model
claims, remains authoritative for `diff` and `changed_files`, and sandbox
cleanup occurs in `finally` on both success and failure.

### 4.5 Sandbox boundary

The Docker command applies these critical restrictions:

```text
--network none
--pids-limit 256
--cap-drop ALL
--security-opt no-new-privileges
--mount type=bind,<run workspace>:/workspace
```

Only the isolated run workspace is mounted. The sandbox receives neither the
OpenAI credential nor the GitHub token and does not receive the Docker socket.
CPU, memory, process count, and command duration are bounded.

### 4.6 Authoritative candidate and publication

Before any push, the publisher verifies:

```text
HEAD == accepted base SHA
git diff --check HEAD -- succeeds
actual binary diff == SolveResult.diff
actual changed paths == SolveResult.changed_files
no matching remote branch
no matching open Pull Request
```

It then creates one deterministic commit and uses a creation lease equivalent
to:

```text
git push --force-with-lease=refs/heads/sage/issue-N: \
  <validated remote> HEAD:refs/heads/sage/issue-N
```

The empty expected value means the remote branch must not exist. The publisher
never targets the default branch. Git credentials are supplied through a
temporary askpass file outside the candidate checkout and deleted in `finally`.

Git validation errors retain bounded, control-safe stderr/stdout so an
offending filename and line can be diagnosed without permitting a filename to
emit a GitHub Actions workflow command.

### 4.7 Immutable action installation

The tracked install template pins all Sage composite action references to:

```text
9556a8b5ec722d7acdaac0d056464ced40d1e6ca
```

That commit contains the `gpt-5.4-mini` default. It must be present in the
canonical public repository before a target workflow can download it. Do not
replace the SHA with `main`, a mutable tag, or the later commit that only
updates documentation or pins.

External actions are also pinned to full commit IDs. Workflow jobs use an empty
top-level permission map and opt into only the permissions each job needs.

## 5. Status, failures, and diagnostics

One hidden invocation marker ties the bot-owned Issue status to the command
comment. Valid workflow states are:

```text
accepted -> working -> pull_request_created
                    -> no_changes
                    -> failed
```

Terminal status cannot be overwritten by another terminal result. Failure
categories distinguish configuration, repository, sandbox, runtime, GitHub,
publication, OpenAI authentication, OpenAI API rejection, quota exhaustion,
and temporary rate limiting without copying raw provider bodies into Issue
comments.

The uploaded diagnostic directory is restricted to:

```text
metadata.json
github.json
agent-final.json
changed-files.json
diff.patch
```

It excludes the checkout, `.git`, model key, GitHub token, webhook event,
materialized Issue context, `.env`, and environment dumps. Retention is seven
days in the tracked workflow.

## 6. API and service boundary

V1.0 relies on standard GitHub repository capabilities through the
job-scoped `GITHUB_TOKEN`:

- GitHub Actions hosted workflow execution;
- Issue, branch, and Pull Request REST endpoints; and
- the repository's normal Actions artifact facility.

It does not require a personal access token, paid GitHub API tier, GitHub App,
external queue, database, or hosted Sage service.

The model boundary uses the operator-provided `OPENAI_API_KEY` and defaults to
`gpt-5.4-mini`. The Sage repository does not purchase capacity, enable billing,
or depend on a paid-only integration. The current operating assumption is that
the repository owner supplies API access from an available free or
credit-backed allocation. OpenAI owns account eligibility, quota, and pricing,
so Sage must not describe all OpenAI API access as universally free. When the
allocation is unavailable, Sage fails safely instead of silently changing
models or enabling a paid service.

## 7. V0.1 compatibility retained

V1.0 extends rather than replaces these interfaces:

- `sage solve --repo ... --issue-file ...` remains available;
- `make first-run REPO=... ISSUE=...` still performs local setup and solve;
- the project-owned LangGraph graph and repository tools are unchanged in
  responsibility;
- local runs still create authoritative `.sage/runs/<run-id>/` artifacts;
- source checkouts remain untouched because Sage works in isolated clones; and
- CLI exit codes remain `0` for a changed candidate, `1` for failure, and `2`
  for a successful no-change solve.

## 8. Repository-wide dead-code audit

The release audit covered every tracked production Python module, Python test,
TypeScript/TSX source file, composite action, workflow, Make target, Docker
definition, package manifest, direct dependency, fixture, and documented
entrypoint.

The audit used repository-wide symbol/call-site searches, Python AST checks for
unreferenced module definitions and imports, public protocol/call-site tracing,
frontend import tracing, package/dependency usage checks, tracked-generated-file
checks, compilation, linting, type checking, and the complete deterministic
test suites.

No confirmed dead production code was found, so no code was deleted. In
particular, the following are intentionally retained:

- empty `__init__.py` files that define Python package boundaries;
- `.sage/.gitkeep`, which preserves the ignored runtime-artifact root;
- package re-exports that form supported import surfaces;
- protocols, factories, and injectable boundaries used by deterministic tests;
- V0.1 local CLI/workflow paths required by the compatibility contract; and
- GitHub finalizer and failure branches that are reached only under interruption
  or recovery conditions.

Deleting any of those as “unused” would either break packaging, reduce testable
dependency injection, or change supported behavior. No dependency was added or
removed as part of this audit.

## 9. Verification and manual acceptance

The required deterministic release command is:

```bash
make v1-check
```

It runs the complete backend tests, byte compilation, focused GitHub tests, and
workflow/action policy tests without a live GitHub or model call. The frontend
is outside this specification but was included in the repository audit through
its existing lint and TypeScript checks.

The model-default feature is specifically verified by:

```bash
env UV_CACHE_DIR=/tmp/sage-v1-uv-cache \
  uv run --project apps/agent pytest \
  apps/agent/tests/test_config.py \
  apps/agent/tests/actions
```

Final local results on 2026-08-22:

- `make v1-check`: passed with 231 full-suite tests, 140 focused GitHub tests,
  6 workflow/action policy tests, and byte compilation;
- `make sandbox-build`: passed;
- `make sandbox-smoke`: passed with Git, Python, and ripgrep in the
  network-disabled image;
- `make github-doctor`: passed;
- `npm run lint`: passed; and
- `tsc --noEmit`: passed.

The default Next.js Turbopack production build could not be completed in this
agent environment because Turbopack was prohibited from binding its internal
local port (`Operation not permitted`). The webpack fallback reached a separate
environmental child-process capture failure while parsing TypeScript
`--showConfig`; running that exact TypeScript command directly succeeded. No
frontend source changed in this release audit, so these environment-specific
build results are reported rather than represented as a passing build.

Manual default-model check:

1. Ensure the target repository has no `OPENAI_MODEL` Actions variable.
2. Install the tracked workflow with the immutable Sage action SHA above.
3. Post one exact `/sage solve` on a small standalone Issue as a write/admin
   user.
4. Confirm the solve log contains
   `model='gpt-5.4-mini' api_key_status=configured`.
5. Confirm no credential value or fingerprint appears.
6. Confirm one correct draft Pull Request or an explicit safe terminal outcome.

The primary live acceptance path has already produced a correct draft Pull
Request. Each production repository should still exercise the permission,
duplicate, no-change, interruption, artifact, and secret-audit scenarios in
[`10_V1.0_testing.md`](10_V1.0_testing.md), because repository policy is
external to Sage's deterministic test suite.

## 10. V1.0 non-goals preserved

V1.0 does not include:

- automatic merge, approval, or ready-for-review transitions;
- arbitrary branch selection or branch overwrite;
- a long-running GitHub App or hosted API service;
- personal access token support as an installation requirement;
- database, queue, polling, or persistent LangGraph checkpoints;
- credentials or network access inside the repository sandbox;
- guaranteed support for self-hosted runners; or
- multi-agent exploration, implementation, and review roles.

These are deliberate release boundaries, not dead code or incomplete primary
V1.0 goals.

## 11. Manual merge handoff

Before manually merging `feat/v1-github-native` into `main`:

1. Review the logical commits and confirm each is signed off.
2. Confirm `make v1-check` passes on the final branch state.
3. Confirm frontend lint and TypeScript checks pass.
4. Confirm `git status --short` contains no uncommitted files.
5. Push the feature branch so immutable commit
   `9556a8b5ec722d7acdaac0d056464ced40d1e6ca` is reachable publicly.
6. Merge through the repository's normal protected-branch process.
7. Copy the final tracked `.github/workflows/sage.yml` into each target
   repository and commit it on that repository's default branch.

Do not rewrite the implementation commit after target repositories begin
pinning it. Future behavior changes require a new implementation commit and a
new explicit immutable pin.
