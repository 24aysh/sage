# Sage V1.0 — Goals and Technology Stack

## 1. Project Context

**Sage** is a software-engineering agent that solves repository-level coding issues.

### Current state: V0.1

V0.1 is already complete and working.

The current workflow is local:

```text
target Git repository
        +
     issue.md
        ↓
      Sage
        ↓
local repository clone
        ↓
repository investigation
        ↓
code changes
        ↓
solved candidate
```

Sage currently:

- accepts a local Git repository;
- accepts an `issue.md` file describing the task;
- clones the repository into an isolated working location;
- investigates the repository;
- modifies the code required to solve the issue;
- uses a custom LangGraph-based agent;
- works through a single-agent workflow.

V1.0 does **not** redefine this coding-agent core.

The purpose of V1.0 is to make the existing Sage agent **GitHub-native**.

---

# 2. V1.0 Primary Goal

The main goal of V1.0 is:

> A repository maintainer should be able to ask Sage to solve a GitHub issue directly from GitHub, without manually cloning the repository or creating an `issue.md` file.

The intended interaction is:

```text
GitHub Issue
     │
     │ maintainer comments
     │
     │ /sage solve
     │
     │ or
     │
     │ /sage fix
     ▼
    Sage
     │
     ▼
isolated repository workspace
     │
     ▼
investigate issue
     │
     ▼
modify repository
     │
     ▼
create Sage branch
     │
     ▼
open Pull Request
     │
     ▼
human review
```

The user should interact with Sage through normal GitHub workflows rather than through a local CLI.

---

# 3. V1.0 User Experience Goals

## 3.1 GitHub-native invocation

A maintainer should be able to invoke Sage by commenting on a GitHub issue.

Supported commands should include:

```text
/sage solve
```

and:

```text
/sage fix
```

Both commands represent the same primary action:

> Solve the issue associated with this GitHub issue thread.

The command syntax should remain intentionally simple in V1.0.

## 3.2 No local setup for the maintainer

The maintainer should not need to:

- clone the target repository locally;
- create an `issue.md` file;
- manually run the Sage CLI;
- manually start Docker;
- manually provide the repository path;
- manually create a branch for Sage;
- manually copy the resulting patch.

GitHub should provide the task context and repository context required for the run.

## 3.3 GitHub issue becomes the task input

The GitHub issue replaces the local `issue.md` input used in V0.1.

Sage should receive the task context required to understand the issue, including:

- issue title;
- issue description;
- relevant issue context;
- repository identity;
- issue number;
- repository base branch/revision.

The GitHub issue remains the human-facing source of the task.

---

# 4. Repository Execution Goal

Sage must continue working against a **real isolated repository checkout**.

It should not attempt to solve repository-level tasks using only GitHub API responses or isolated file snippets.

For every invocation:

```text
GitHub repository
       ↓
fresh hosted runner
       ↓
isolated repository checkout
       ↓
Docker sandbox
       ↓
Sage coding workflow
```

Each Sage run should receive its own isolated working environment.

Runs must not share a writable repository workspace.

---

# 5. GitHub Actions as the V1.0 Execution Platform

V1.0 should use **GitHub Actions hosted runners** as the execution environment.

The intended model is:

```text
/sage solve
     ↓
GitHub issue comment event
     ↓
GitHub Actions
     ↓
fresh hosted runner
     ↓
trusted Sage controller
     ↓
Docker sandbox
     ↓
repository solve
     ↓
Pull Request
```

This gives V1.0 an event-driven execution model without requiring Sage to run on a permanently hosted server.

V1.0 should therefore require:

- no always-running Sage process;
- no continuously running VM;
- no separately hosted backend service;
- no polling loop waiting for GitHub issues;
- no `/sage awake` mechanism.

GitHub Actions is responsible for starting compute when Sage is invoked.

---

# 6. Docker Sandbox Goal

Docker remains the repository execution boundary in V1.0.

The GitHub Actions runner acts as the trusted controller environment.

The target repository executes inside a disposable Docker sandbox.

```text
GitHub Actions runner
│
├── Sage controller
├── LangGraph agent
├── model/API credentials
├── GitHub workflow credentials
│
└── Docker sandbox
      ├── target repository
      ├── repository tools
      ├── repository commands
      ├── NO model API credentials
      └── NO GitHub publishing credentials
```

The sandbox should preserve the security model established in V0.1:

- disposable execution;
- restricted filesystem access;
- bounded CPU and memory;
- bounded process count;
- command timeouts;
- no Docker socket inside the sandbox;
- no privileged container;
- minimal mounts;
- provider secrets kept outside repository execution;
- GitHub credentials kept outside repository execution.

The repository should be treated as untrusted input.

---

# 7. Sage Agent Goal

V1.0 should continue using the existing **custom LangGraph-based Sage agent**.

The core coding behavior remains conceptually the same as V0.1:

```text
understand issue
     ↓
inspect repository
     ↓
locate relevant code
     ↓
reason about change
     ↓
modify code
     ↓
inspect resulting repository state
     ↓
finish with candidate solution
```

V1.0 is primarily a GitHub integration milestone.

It should not require a redesign of the working Sage reasoning engine simply because the task now originates from GitHub.

---

# 8. GitHub Authorization Goal

A random GitHub user must not be able to trigger paid Sage runs on a repository.

Before starting the agent, V1.0 should determine whether the user who invoked Sage is authorized.

Expected authorized actors include repository users such as:

- repository owner;
- organization member where appropriate;
- repository collaborator;
- user with sufficient repository permissions.

Unauthorized `/sage solve` or `/sage fix` commands should not start the coding agent.

This authorization check should happen before expensive model execution.

---

# 9. Issue Command Handling Goals

V1.0 should correctly distinguish Sage commands from ordinary issue conversation.

A Sage run should begin only when a supported invocation command is present.

Primary commands:

```text
/sage solve
/sage fix
```

The system should also avoid accidentally treating Pull Request conversation comments as new issue-solving requests when the workflow is intended for GitHub Issues.

Repeated commands for the same issue should not accidentally create uncontrolled duplicate runs.

---

# 10. Repository Revision Goal

Every Sage run should operate against a clearly defined repository revision.

At the beginning of the run Sage should know:

```text
repository
issue number
base branch
exact base commit
```

The code Sage investigates and modifies must correspond to that exact repository state.

This prevents Sage from reasoning about one version of the repository and publishing against another without knowing that the base changed.

---

# 11. Pull Request Goal

The primary output of a successful V1.0 run is a **Pull Request**.

Sage should not directly modify or push to the repository's default branch.

The GitHub-native output should conceptually be:

```text
Issue
  ↓
Sage run
  ↓
Sage-owned branch
  ↓
commit containing solution
  ↓
Pull Request
```

The Pull Request should make the result easy for a human maintainer to inspect.

The PR should clearly identify:

- the GitHub issue being solved;
- that the change was generated by Sage;
- a concise summary of the change;
- the files changed;
- useful run information;
- any remaining uncertainty or limitation reported by Sage.

The normal human review boundary is the Pull Request itself.

V1.0 should **not auto-merge** Sage changes.

---

# 12. GitHub Issue Feedback Goal

The GitHub issue should visibly communicate the Sage run state.

The maintainer should not have to inspect GitHub Actions logs just to know whether Sage started or completed.

At minimum, the issue interaction should make it clear when Sage:

```text
accepted the command
started work
completed successfully
created a Pull Request
failed before producing a Pull Request
```

The final successful issue response should direct the maintainer to the created Pull Request.

Failure messages should be concise and understandable rather than exposing large internal stack traces.

---

# 13. Failure Behavior Goal

A failed Sage run should fail safely.

If Sage cannot produce a valid candidate, V1.0 should:

- avoid pushing incomplete work to the default branch;
- avoid opening a misleading successful PR;
- clean up disposable repository execution;
- preserve useful GitHub Actions logs;
- communicate failure clearly on the issue;
- make the failure understandable enough for the maintainer to retry or investigate.

A failure should never leave Sage with uncontrolled credentials or a persistent execution container.

---

# 14. Isolation Between Runs

Every GitHub issue solve should be independent.

For example:

```text
Issue #101 → Runner A → Sandbox A
Issue #102 → Runner B → Sandbox B
Issue #103 → Runner C → Sandbox C
```

Sage runs should not share:

- writable repository state;
- active Docker containers;
- temporary branch state before publishing;
- agent execution state.

This ensures that multiple issues can be handled independently.

---

# 15. Security Goals

V1.0 introduces GitHub credentials in addition to model credentials, so the trust boundary becomes especially important.

## Trusted environment

The GitHub Actions runner/controller may contain:

```text
model API credential
GitHub workflow credential
Sage controller
LangGraph orchestration
publishing logic
```

## Untrusted execution environment

The Docker sandbox contains:

```text
repository
source code
repository instructions
shell commands
build/runtime commands
```

but should not contain:

```text
model/API credentials
GitHub publishing credentials
host credentials
Docker socket
unnecessary host filesystem mounts
```

Repository files, issue text, comments, command output, and source-code comments should all be considered potentially untrusted content.

Security policy must be enforced by normal software boundaries rather than relying only on the model to behave correctly.

---

# 16. Cost Goal

V1.0 should preserve the project's low-cost architecture.

The primary execution platform is:

```text
GitHub Actions hosted runner
+
Docker
```

There should be no separately hosted always-on Sage backend for V1.0.

The main variable cost should remain model/API usage and any GitHub Actions usage applicable to the repository/account.

The architecture should avoid introducing infrastructure whose only purpose is to keep Sage continuously online.

---

# 17. V1.0 Technology Stack

| Layer | V1.0 Choice |
|---|---|
| Agent name | **Sage** |
| Primary language | **Python** |
| Agent architecture | **Custom LangGraph-based agent** |
| GitHub trigger | **GitHub Actions `issue_comment` event** |
| User command | **`/sage solve` and `/sage fix`** |
| Compute | **GitHub-hosted Actions runner** |
| Repository checkout | **Git / GitHub checkout on hosted runner** |
| Repository execution | **Disposable Docker sandbox** |
| Git operations | **Git CLI** |
| GitHub interaction | **GitHub APIs / GitHub workflow tooling** |
| Task source | **GitHub Issue** |
| Result | **Sage branch + Pull Request** |
| Model/API layer | **Existing Sage model integration** |
| Secrets | **GitHub Actions secrets/environment, controller only** |
| Run logs | **GitHub Actions logs** |
| Run artifacts | **GitHub Actions artifacts where useful** |
| Frontend | **Existing Next.js/TypeScript landing page; not required for issue execution** |
| Persistent backend server | **None for V1.0** |
| Database | **None required for V1.0** |
| Queue infrastructure | **None required; GitHub Actions triggers execution** |
| Repository sandbox provider | **Docker** |

---

# 18. V1.0 Feature Set

A complete V1.0 should support:

- GitHub-native invocation from an issue;
- `/sage solve`;
- `/sage fix`;
- authorization before model execution;
- GitHub issue used directly as task input;
- repository automatically checked out;
- exact base repository revision associated with the run;
- fresh GitHub-hosted runner for the job;
- disposable Docker repository sandbox;
- existing custom LangGraph Sage agent used for solving;
- repository exploration and code modification;
- independent workspace for every run;
- model credentials isolated from repository execution;
- GitHub credentials isolated from repository execution;
- Sage-owned branch for a successful candidate;
- commit containing the Sage solution;
- Pull Request creation;
- PR linked back to the source issue;
- concise PR summary;
- changed-file information;
- remaining uncertainty surfaced to the maintainer;
- issue-level run status communication;
- clear failure reporting;
- cleanup after the run;
- no direct push to the default branch;
- no automatic merge;
- no always-running server.

---

# 19. V1.0 Non-Goals

V1.0 should remain focused.

The following are **not required for V1.0**:

- multi-agent Sage;
- separate planner/implementer/reviewer agents;
- independent cross-model reviewer;
- autonomous PR review loops;
- automatic merging;
- always-running backend;
- GitHub App infrastructure;
- external queue;
- Redis;
- PostgreSQL;
- Kubernetes;
- cloud sandbox service;
- persistent cross-run memory;
- web dashboard for starting runs;
- broad command syntax beyond the core Sage issue-solving workflow.

Those capabilities can be considered in later versions.

---

# 20. V1.0 Definition of Done

V1.0 is complete when the complete user journey works:

```text
Maintainer opens or selects a GitHub issue
                ↓
Maintainer comments /sage solve
                ↓
Sage verifies that the user may invoke it
                ↓
GitHub Actions starts a fresh hosted runner
                ↓
Repository is checked out at a known base revision
                ↓
Disposable Docker sandbox is created
                ↓
Existing LangGraph Sage agent receives the issue
                ↓
Sage investigates and modifies the repository
                ↓
Candidate changes are collected
                ↓
Sage creates its own branch
                ↓
Sage opens a Pull Request
                ↓
Issue receives the result / PR link
                ↓
Human maintainer reviews the Pull Request
```

The defining difference between the versions is:

```text
V0.1
local repository + issue.md
        ↓
Sage
        ↓
local candidate solution


V1.0
GitHub issue + /sage solve
        ↓
GitHub Actions + Docker + Sage
        ↓
Pull Request
```

V1.0 should make Sage feel like a native GitHub collaborator while preserving the isolated execution and custom LangGraph agent architecture already proven in V0.1.
