# Sage V1.0 GitHub Actions Setup and Manual Testing Guide

## Document status

This guide is the user-facing companion to:

- [`08_V1.0_design.md`](08_V1.0_design.md); and
- [`09_V1.0_implementation_plan.md`](09_V1.0_implementation_plan.md).

It explains the complete intended journey from enabling GitHub Actions to
asking Sage to solve an issue with `/sage solve`.

### Current implementation status

V1.0 is being delivered in reviewable parts. Parts 1 and 2 currently provide:

- exact `/sage solve` and `/sage fix` parsing;
- typed and bounded `issue_comment` event loading;
- GitHub.com repository, issue, actor, comment, run, and base-SHA validation;
- bounded GitHub controller settings isolated from model settings;
- pure write/admin authorization policy;
- a typed, bounded GitHub REST client with no additional runtime dependency;
- permission, open-PR, remote-branch, and status-marker gate checks;
- accepted, unauthorized, existing-PR, and existing-branch gate statuses;
- create-or-reuse status reconciliation after an ambiguous API response;
- validated non-secret GitHub Actions outputs;
- the internal `sage github gate` automation command;
- an offline `make github-test` command;
- reusable trusted host-Git and atomic artifact primitives; and
- deterministic tests and sanitized event fixtures.

The following pieces are still required before a real GitHub comment can run
Sage:

- issue-context collection;
- GitHub solve orchestration;
- secure branch/commit publication;
- draft Pull Request creation;
- working and terminal issue status transitions;
- composite GitHub Actions;
- the enabled repository workflow; and
- a concrete immutable Sage release SHA.

Do **not** create a production workflow from guessed action names or a branch
reference while those parts are incomplete. The setup steps below become
runnable when this status section says **V1.0 live path available** and the
installation section contains a concrete tested 40-character Sage commit SHA.

This explicit status prevents a new user from getting stuck with a workflow
that can start but cannot authorize, solve, publish, or report failure safely.

## 1. What the finished workflow does

After one-time repository setup, a maintainer uses Sage entirely from GitHub:

```text
GitHub Issue
    │
    │ maintainer comments exactly: /sage solve
    ▼
Sage authorization gate
    │
    ├── confirms this is an Issue, not a Pull Request
    ├── confirms the actor has write/admin permission
    ├── confirms no Sage PR/branch already owns the issue
    └── records the exact default-branch commit
    ▼
fresh GitHub-hosted runner
    │
    ├── pinned Sage controller
    ├── exact target checkout
    └── disposable network-disabled Docker sandbox
            │
            └── existing LangGraph Sage solver
    ▼
sage/issue-<number> branch
    │
    ▼
draft Pull Request linked from the Issue
```

Sage never needs to be kept awake. There is no background server, polling
process, database, or queue to operate.

## 2. Safety expectations

Before setup, understand these boundaries:

- The target repository and issue text are untrusted input.
- Repository commands run inside a disposable Docker sandbox with no network.
- The sandbox does not receive `OPENAI_API_KEY` or `GITHUB_TOKEN`.
- The trusted Actions controller performs model calls and deterministic GitHub
  publication.
- Sage pushes only `sage/issue-<number>`.
- Sage does not push the default branch, overwrite an existing branch,
  auto-merge, or mark its own draft PR ready.
- A human must inspect the Pull Request before merging.
- A normal repeated unit-test run does not call a paid model or GitHub API.

If a workflow or log asks you to paste a token into an issue, commit it to a
file, print it, or place it inside a Docker command, stop. That is not the
documented Sage flow.

## 3. Prerequisites

### 3.1 GitHub repository access

You need:

- a repository hosted on GitHub.com;
- permission to change repository Actions settings;
- permission to add Actions secrets;
- permission to add a workflow to the default branch;
- a maintainer account with calculated `write` or `admin` repository access;
- GitHub Actions enabled for the repository; and
- GitHub-hosted Linux runners allowed by repository/organization policy.

For the first live test, use a private throwaway repository or a low-risk
canary repository. Do not start with a production repository containing
sensitive deployment credentials.

### 3.2 OpenAI access

You need a valid OpenAI API key with access to the model configured for Sage.
Model usage can incur cost. Use a small, clearly bounded issue for the first
test and keep the existing `SAGE_MAX_TURNS` limit.

### 3.3 Repository suitability

The V1.0 sandbox image contains the tools documented by Sage. A repository that
requires additional system services, private package registries, network
downloads, or credentials during tests may not be fully testable inside the
network-disabled sandbox.

That limitation should be written in the issue so the agent can make a safe
change and report remaining uncertainty instead of pretending all checks ran.

## 4. One-time GitHub Actions setup

Perform this section as a repository administrator.

### Step 1 — Confirm the default branch

On the repository home page, identify the default branch, commonly `main`.
Sage records the exact commit on that branch when the issue command event is
created.

The `issue_comment` workflow file must exist on the default branch. GitHub does
not trigger this event from a workflow that exists only on an unmerged feature
branch.

### Step 2 — Enable the Actions used by Sage

Open:

```text
Repository → Settings → Actions → General
```

Under the Actions policy, allow the specific pinned actions used by the Sage
installation template. Organization policy can override repository policy. If
the settings are disabled or restricted, ask an organization administrator to
allow the exact action repositories and immutable SHAs.

Do not solve this by changing the Sage references from a full commit SHA to a
moving branch.

### Step 3 — Permit workflow Pull Request creation

On the same Actions settings page, find **Workflow permissions** and enable:

```text
Allow GitHub Actions to create and approve pull requests
```

Sage uses the create capability only. Sage does not approve or merge its own
Pull Request.

If this repository inherits a locked organization policy, an organization
administrator must change that policy. The relevant GitHub documentation is
[Managing GitHub Actions settings for a repository](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/enabling-features-for-your-repository/managing-github-actions-settings-for-a-repository).

### Step 4 — Keep default-branch protection enabled

Do not remove branch protection to make Sage easier to test. Keep the normal
human review, required checks, and merge restrictions on the default branch.

Sage creates a draft Pull Request precisely so those repository controls remain
the final review boundary.

### Step 5 — Add the OpenAI key as an Actions secret

Open:

```text
Repository → Settings → Secrets and variables → Actions
```

Select **New repository secret** and use this exact name:

```text
OPENAI_API_KEY
```

Paste the key into the secret value and save it.

Important:

- Do not put the key in `.env` and commit it.
- Do not add it as a plain Actions variable.
- Do not paste it into an issue or Pull Request.
- Do not print it to check whether it works.
- GitHub will not show the saved value again; that is expected.

If the key must be rotated, create a replacement in the OpenAI account and
update the repository secret. Do not try to recover an old value from logs.

### Step 6 — Install the pinned Sage workflow

This step is intentionally blocked until the V1.0 composite actions have been
implemented and assigned a tested immutable release commit.

When available, copy the tracked Sage installation template into:

```text
.github/workflows/sage.yml
```

The gate and solve action references must look like this shape:

```yaml
uses: 24aysh/sage/.github/actions/sage-gate@<40-character-tested-sha>
```

```yaml
uses: 24aysh/sage/.github/actions/sage-solve@<same-40-character-tested-sha>
```

Do not literally keep `<40-character-tested-sha>`. Do not replace it with
`main`, `v1`, or another moving ref. This guide will contain the concrete SHA
after the action implementation passes the canary acceptance suite.

Use the whole maintained template. Do not copy only the trigger. The complete
workflow also owns:

- exact command and Issue-only filters;
- empty top-level permissions;
- separate gate/solve/finalizer job permissions;
- concurrency for one active run per issue;
- `cancel-in-progress: false`;
- exact-SHA target checkout;
- `persist-credentials: false`;
- job timeouts;
- model secret scoping; and
- safe failure status repair.

Commit the workflow through normal review and merge it to the default branch.

### Step 7 — Confirm the workflow is visible

Open the repository's **Actions** tab. The Sage workflow name from the template
should be visible after the workflow reaches the default branch.

If GitHub reports an invalid workflow:

1. do not comment `/sage solve` repeatedly;
2. open the failing workflow annotation;
3. compare the file to the tracked template exactly;
4. confirm every `uses:` SHA has the required length; and
5. fix the workflow through a reviewed commit.

## 5. Create a safe first issue

Choose a small deterministic problem. Avoid broad requests such as “improve the
whole project” for the first run.

### Example issue title

```text
Handle division by zero in the calculator
```

### Example issue body

```markdown
## Problem

Calling `divide(10, 0)` currently raises an unclear low-level error.

## Expected behavior

- Raise `ValueError` with the message `divisor must not be zero`.
- Preserve behavior for non-zero divisors.
- Add or update focused unit tests.

## Verification

Run:

`python3 -m unittest discover -v`

## Scope

Do not change unrelated calculator operations or dependencies.
```

A useful issue contains:

- the observed behavior;
- the desired behavior;
- reproducible inputs;
- acceptance criteria;
- a relevant test command when known;
- explicit non-goals; and
- required compatibility constraints.

Do not include secrets, private credentials, production data, or unnecessary
personal information. The issue body and selected discussion become model task
context and may be retained in the local run artifacts on the ephemeral runner.

## 6. Invoke Sage

An authorized maintainer adds a new standalone comment to the Issue:

```text
/sage solve
```

The alias below has identical semantics:

```text
/sage fix
```

The comment must contain exactly one of those strings. These do not invoke
Sage:

```text
please /sage solve
```

```text
/sage solve now
```

```text
 /sage solve
```

```markdown
`/sage solve`
```

The command is case-sensitive. `/SAGE SOLVE` is not accepted.

Do not place the command on a Pull Request conversation. GitHub emits the same
event family for Issue and Pull Request comments, but Sage intentionally
accepts Issue comments only.

## 7. What you should see

### 7.1 Accepted

After the gate validates the event, actor permission, existing branch, and
existing PR, Sage creates or reuses one status comment. It should say that the
command was accepted and show:

- the invoking actor;
- the issue number;
- a short exact base SHA; and
- a link to the Actions run.

No accepted status means the solve has not safely started. Check the
troubleshooting section before retrying.

### 7.2 Working

The same status comment changes to working after the separate solve job repeats
authorization and prepares the exact target checkout.

In the Actions run, the expected high-level stages are:

```text
gate
  validate event
  check permission
  check duplicate branch/PR
  create accepted status

solve
  check out exact base
  set up locked Sage environment
  build Docker sandbox
  assemble bounded issue context
  run existing LangGraph solver
  validate Git diff
  commit and push Sage branch
  open draft Pull Request

finalize
  preserve an existing terminal status
  or repair an interrupted run with a safe failure status
```

The logs must never display an OpenAI key, GitHub token, authorization header,
credential-bearing remote URL, or complete environment dump.

### 7.3 Completed with a Pull Request

For a successful change, the status comment links a draft Pull Request. The PR
should contain:

- a title beginning with `Sage:`;
- a generated-by-Sage notice;
- `Closes #<issue-number>`;
- the agent summary;
- the authoritative changed-file list;
- any remaining uncertainty;
- the original exact base SHA;
- the current default-branch SHA when checked before publication;
- a base-advanced warning when applicable; and
- the Actions run link.

The branch must be:

```text
sage/issue-<issue-number>
```

The default branch must remain unchanged until a human merges the reviewed PR.

### 7.4 Completed with no changes

The agent may conclude without a Git diff. In that case:

- the status should explicitly say no repository changes were produced;
- there should be no new Sage branch;
- there should be no misleading success PR; and
- the summary/uncertainty should help the maintainer decide whether to clarify
  the issue and retry.

No-change is a completed solve outcome, not an infrastructure crash.

## 8. Review the candidate safely

Before merging:

1. confirm the PR base is the expected default branch;
2. confirm the head is `sage/issue-<number>`;
3. inspect every changed file;
4. compare the changes to the issue acceptance criteria;
5. inspect tests the agent added or changed;
6. inspect workflow, dependency, build, and deployment changes especially
   carefully;
7. read the remaining uncertainty section;
8. run the repository's normal trusted CI after approving it when required;
9. run additional manual tests if the issue is high risk; and
10. mark ready/merge only through the repository's normal human process.

Treat code generated by Sage as an untrusted proposal until reviewed. A draft
PR is not an assertion that the code is safe to deploy.

## 9. Pull Request checks may wait for approval

GitHub currently treats Pull Requests created with a workflow's
`GITHUB_TOKEN` specially. A created or updated PR can produce
`pull_request` workflow runs that wait for a write user to approve them. This
prevents recursion and unreviewed workflow execution.

If checks show **Waiting for approval**:

1. inspect the proposed diff first, especially workflow/build files;
2. use GitHub's normal approval control for the workflow run;
3. wait for the checks to complete; and
4. do not replace `GITHUB_TOKEN` with a PAT merely to skip the approval.

See GitHub's [`GITHUB_TOKEN` documentation](https://docs.github.com/en/actions/concepts/security/github_token) for the current behavior.

## 10. Authorization behavior

Sage uses GitHub's calculated legacy repository permission:

| Calculated permission | Result |
| --- | --- |
| `admin` | allowed |
| `write` | allowed |
| maintain role mapped by GitHub to `write` | allowed |
| `read` | denied |
| triage role mapped by GitHub to `read` | denied |
| `none` or actor not found | denied |

Being the issue author, an organization member, or having an
`author_association` label is not sufficient by itself. The effective
repository permission is authoritative.

An unauthorized command should receive a concise denial and must not start the
solve job or expose/use `OPENAI_API_KEY`.

## 11. Duplicate and retry behavior

Sage allows one active branch per issue.

### Existing open Sage PR

If `sage/issue-<number>` already has an open PR, a repeated command should link
the existing PR and skip the model run.

Continue the review in that PR. Do not delete the branch just to make Sage run
again.

### Existing branch without an open PR

This usually means publication pushed the branch but PR creation failed, or a
human created the reserved branch. Sage must not overwrite it.

Choose one deliberate recovery:

1. inspect the branch and manually open a PR from it; or
2. after confirming it is unwanted and recoverable, delete it through normal
   GitHub controls, then add a new exact Sage command.

Do not force-push or delete the default branch.

### Command repeated while a run is active

The active run is not canceled. GitHub concurrency keeps at most the relevant
pending retry according to the installed template. When a pending command
starts, Sage repeats authorization and duplicate checks.

Do not post the command repeatedly to “wake” Sage. Inspect the linked Actions
run instead.

## 12. Troubleshooting

Use the smallest safe diagnostic. Never paste secrets into a log or support
report.

### Symptom: no workflow run appears

Likely causes:

- the workflow is not on the default branch;
- Actions is disabled or restricted;
- the comment is not an exact command;
- the comment was edited instead of newly created;
- the comment is on a Pull Request; or
- the workflow YAML is invalid.

Diagnostics:

1. confirm `.github/workflows/sage.yml` exists on the default branch;
2. open the Actions tab and check for workflow validation annotations;
3. copy the comment into a plain-text editor and check invisible whitespace;
4. verify the event was a new Issue comment; and
5. compare the workflow to the exact pinned template.

Safe fix: correct the setup, then create one new exact command comment.

### Symptom: command is denied

Likely cause: the invoking account does not currently have calculated write or
admin permission.

Diagnostic: ask a repository administrator to inspect the user's effective
repository access, including team and organization roles.

Safe fix: have an authorized maintainer invoke Sage, or deliberately grant the
needed repository role through normal GitHub administration.

Do not change the workflow to trust `author_association` or every organization
member.

### Symptom: gate fails before accepted status

Likely causes:

- `GITHUB_TOKEN` permissions are restricted by policy;
- the GitHub API is unavailable or rate-limited;
- the installed action pin is disallowed; or
- event/repository data did not validate.

Diagnostics:

1. inspect the gate job's safe error category and request ID;
2. check GitHub's status page if API failures are widespread;
3. confirm the workflow's gate permissions match the template; and
4. confirm the action SHA is the documented tested SHA.

Safe fix: correct policy/configuration or wait for GitHub recovery, then create
one new command. No model charge should occur for a rejected gate.

### Symptom: `OPENAI_API_KEY` is reported missing

Likely causes:

- the secret name is misspelled;
- it was added to an environment that the job does not use;
- organization policy blocks it; or
- the copied workflow did not pass it only to the solve action.

Diagnostic: open **Settings → Secrets and variables → Actions** and confirm a
secret named exactly `OPENAI_API_KEY` exists. GitHub will not reveal its value.

Safe fix: replace the secret with a known valid key and rerun with a new command.

Do not print the secret or convert it to a non-secret variable.

### Symptom: sandbox image fails to build or Docker cannot start

Likely causes:

- transient package/image registry failure during the trusted image build;
- hosted-runner Docker failure;
- organization runner restrictions; or
- an invalid pinned Sage Dockerfile/action revision.

Diagnostics:

1. inspect only the build/start error, not the environment;
2. confirm the job is on the supported GitHub-hosted Linux runner;
3. check service status; and
4. compare the action SHA to the tested release.

Safe fix: retry after transient service recovery or update to a reviewed tested
Sage pin. A failed sandbox setup must not create a candidate branch.

### Symptom: agent run fails

Likely causes:

- invalid/expired API key;
- model access or provider outage;
- model turn limit;
- repository command timeout;
- insufficient issue context; or
- the repository needs network/services unavailable in the sandbox.

Diagnostics:

1. read the issue's safe failure category;
2. follow the Actions run link;
3. inspect model-turn/tool names and timeout categories, not secret values;
4. verify the issue has reproducible acceptance criteria; and
5. verify tests can run without forbidden credentials/network.

Safe fix: correct credentials/configuration, clarify the issue, or adapt the
repository's offline test path, then create one new exact command.

### Symptom: run finishes with no changes

Likely causes:

- the requested behavior already exists;
- the issue is ambiguous;
- relevant code could not be located;
- the change is impossible within current tools; or
- the agent stopped with documented uncertainty.

Diagnostic: read the terminal summary and uncertainty, then compare the exact
base SHA to the repository state you expected.

Safe fix: add concrete reproduction/acceptance details to the issue and invoke
Sage again. Do not create an empty branch manually.

### Symptom: push succeeds but no Pull Request appears

Likely causes:

- Actions is not allowed to create PRs;
- the PR API failed after branch creation; or
- branch protection/repository policy rejected publication.

Diagnostics:

1. inspect the failure status for a `sage/issue-<number>` branch link;
2. check **Settings → Actions → General → Workflow permissions**;
3. inspect the branch contents before any cleanup; and
4. inspect the PR API safe status/request ID.

Safe fix: enable the required setting or manually create a draft PR from the
preserved branch. Delete the branch only after confirming it is unwanted.

### Symptom: default branch advanced during the solve

Normal advance: the PR includes both SHAs and a warning. Review conflicts and
run current CI; Sage does not silently rebase.

Rewritten base: Sage stops before pushing and asks for a retry because the
original base is no longer an ancestor.

Safe fix for rewritten base: verify the intentional default-branch rewrite,
then add one new Sage command so the agent investigates the new exact base.

### Symptom: Actions job times out or is canceled

The hosted runner is disposable, so its container and temporary credentials do
not persist. The finalizer should mark a non-terminal issue status as failed
when GitHub schedules it.

Diagnostic: inspect the job duration, last safe phase, model turns, and command
timeouts.

Safe fix: address the slow/failing boundary before retrying. Do not simply
increase every timeout or remove the turn limit.

### Symptom: expected PR checks do not start

If the PR was created with `GITHUB_TOKEN`, its checks may wait for maintainer
approval. Inspect the PR banner and approve the workflow only after reviewing
the diff.

Do not add a PAT or GitHub App token in V1.0 to bypass this safety behavior.

## 13. Inspect run artifacts

The enabled workflow should upload only a short-retention diagnostic bundle:

```text
metadata.json
github.json
agent-final.json       when available
changed-files.json     when available
diff.patch             when available
```

It must not upload:

- the complete candidate checkout or `.git` directory;
- the generated issue context;
- `.env` files;
- the webhook payload;
- runner environment dumps; or
- credentials.

Use the Pull Request for normal code review. Download artifacts only when
diagnosing a run, store them according to the repository's data policy, and
delete local copies when no longer needed.

## 14. Local deterministic validation for developers

The current Parts 1 and 2 can be tested without GitHub credentials, Docker, a
network connection, or a model call. Start with the dedicated command from the
repository root:

```bash
make github-test
```

Expected result:

```text
<pytest progress> [100%]
```

The exact test count will grow as later V1.0 parts are implemented. A zero exit
code and no failure summary are authoritative; do not depend on a fixed count.

This focused command verifies:

- exact command and event parsing;
- malformed or untrusted event rejection;
- controller configuration that does not require `OPENAI_API_KEY`;
- every implemented REST endpoint through an offline fake transport;
- fixed API host, authorization/API-version headers, encoding, and timeouts;
- bounded GET/PATCH retries and no blind POST retry;
- safe error messages that omit token and response contents;
- denial for read/none permission before duplicate checks;
- open-PR and existing-branch duplicate outcomes;
- newest-page bounded status-marker discovery;
- bot-authored status reuse instead of user-marker spoofing;
- ambiguous create-comment reconciliation;
- single-line non-secret Actions outputs; and
- continued parsing of the existing local `sage solve` command.

To inspect the new automation command without calling GitHub:

```bash
uv run --project apps/agent sage github gate --help
```

Do not invoke `sage github gate` with a fabricated production event or token.
It is an internal Actions controller command and can create or update an Issue
comment. The later composite action will supply its validated event path,
repository token, and `GITHUB_OUTPUT` file. Until that action exists, use the
offline fake tests above.

The equivalent direct focused commands are:

```bash
uv run --project apps/agent pytest apps/agent/tests/integrations/github
uv run --project apps/agent pytest apps/agent/tests/test_cli.py
```

If the environment cannot write the default uv cache:

```bash
UV_CACHE_DIR=/tmp/sage-v1-uv-cache \
  uv run --project apps/agent pytest apps/agent/tests/integrations/github
```

Run all deterministic backend checks:

```bash
make check
```

If `make github-test` reports that `uv` is missing, install `uv` using its
official installation instructions, then run `make setup` and retry. If the
cache is not writable, use the `UV_CACHE_DIR` form above. These focused checks
do not need Docker; a Docker error means a broader setup or solve command was
run instead.

These commands validate fixtures, REST behavior, gate decisions, statuses, and
output handling. They do not prove that the not-yet-delivered live GitHub
workflow can construct context, run the model, publish a branch, or open a PR.

Later implementation parts will add documented commands for context rendering,
publisher integration, Actions validation, and a V1 aggregate check. Do not
assume those targets exist until `make help` lists them.

## 15. Required canary acceptance run

Before enabling Sage in a production repository, verify all scenarios in a
private/throwaway canary:

| Scenario | Expected result |
| --- | --- |
| Ordinary Issue comment | no Sage job/status/model call |
| Exact command on Pull Request | ignored |
| Read-only actor command | denied before solve |
| Write actor `/sage solve` | accepted, working, terminal status |
| Write actor `/sage fix` | same semantics as solve |
| Small successful issue | deterministic branch and draft PR |
| Repeat while running | no concurrent second paid solve |
| Repeat with open Sage PR | existing PR linked; no model run |
| No-change issue | terminal no-change; no branch/PR |
| Invalid model key | safe failure; no branch; container cleaned |
| PR creation disabled | preserved orphan branch and recovery guidance |
| Two different issues | independent runs, branches, and containers |
| Artifact/log audit | no GitHub/OpenAI credential or environment dump |

Record:

- the tested Sage action commit SHA;
- canary repository;
- date/time;
- workflow run links;
- resulting PR link;
- checks performed; and
- any limitation accepted for rollout.

Do not record secret values.

## 16. Disable or remove Sage

To stop new invocations immediately:

1. disable the Sage workflow from the Actions UI, or remove
   `.github/workflows/sage.yml` through a reviewed commit;
2. remove/rotate `OPENAI_API_KEY` if Sage is being retired;
3. inspect any active Actions run and cancel it through GitHub if necessary;
4. review open Sage PRs normally; and
5. delete Sage branches only after confirming their work is no longer needed.

Disabling the GitHub workflow does not remove the local V0.1 CLI or existing run
artifacts. It does not require rewriting history or force-deleting branches.

## 17. Information to include in a bug report

Provide:

- repository visibility category (public/private), not private source content;
- issue number and safe URL when shareable;
- Actions run URL and run attempt;
- Sage action commit SHA;
- exact command spelling;
- short base SHA;
- safe failure category/message;
- whether an open Sage branch/PR exists;
- whether the actor has write/admin permission;
- relevant bounded logs with sensitive content removed; and
- steps already tried.

Never include:

- `OPENAI_API_KEY`;
- `GITHUB_TOKEN`;
- authorization headers;
- credential-bearing URLs;
- full environment dumps;
- private issue/repository content outside its approved audience; or
- downloaded artifact bundles without reviewing them first.

## 18. Final success checklist

The first live solve is successful only when:

- [ ] the workflow is installed on the default branch;
- [ ] both Sage action references use the documented immutable commit SHA;
- [ ] an authorized user posted one exact command on an Issue;
- [ ] the issue showed accepted and working states;
- [ ] the Actions solve used the recorded exact base SHA;
- [ ] repository commands ran in the credential-free Docker sandbox;
- [ ] a `sage/issue-<number>` branch was created without changing default;
- [ ] a draft Pull Request links the source issue;
- [ ] changed files, summary, base, run, and uncertainty are visible;
- [ ] a human reviewed the complete diff;
- [ ] relevant tests/checks passed or limitations are understood;
- [ ] logs and artifacts contain no credentials; and
- [ ] repeated commands do not create duplicate concurrent paid work.

Until the current implementation status at the top says the live path is
available and supplies the tested SHA, only the local deterministic Parts 1–2
checks are expected to pass.
