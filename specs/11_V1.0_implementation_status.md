As of 2026-08-20, the V0.1-to-V1.0 implementation is complete in the local
feature branch. V1.0 now has an end-to-end GitHub Actions path from an exact,
authorized Issue comment through an isolated solve to a creation-only branch

The composite actions are pinned by the tracked workflow to immutable commit:


## Implemented V1.0 behavior

### 1. Event validation and authorization

- Accepts only a newly created standalone Issue comment whose body is exactly
  `/sage solve` or `/sage fix`.
- Rejects Pull Request comments, Issue-body text, whitespace variants, mixed
  prose, malformed payloads, repository mismatches, and unsupported hosts.
- Validates repository, issue, actor, comment, workflow run, default branch, and
  event base SHA into typed bounded models.
- Uses GitHub's calculated repository permission and allows only `write` or
  `admin`.
- Performs authorization and duplicate checks without loading model settings or
  exposing `OPENAI_API_KEY`.
- Repeats permission and duplicate checks in the solve job to close the gap
  between gate acceptance and paid execution.

### 2. GitHub API and status ownership

- Uses the existing standard-library typed REST client with a fixed GitHub API
  host, explicit API version, bounded payloads, encoding, timeouts, and safe
  errors.
- Bounds and retries safe reads/updates while avoiding blind POST retries.
- Reconciles ambiguous status-comment and Pull Request creation responses.
- Reuses only bot-authored invocation markers so user text cannot impersonate
  a controller status.
- Enforces the state machine `accepted -> working -> terminal`, where terminal
  is PR-created, no-change, or failed.
- Preserves terminal status during finalization and repairs an interrupted
  non-terminal run with a sanitized failure status.

### 3. Bounded Issue context

- Retrieves the current Issue plus a newest-page-bounded comment window.
- Excludes command comments, Sage status comments, the invoking command itself,
  and comments created after the invocation.
- Renders relevant discussion chronologically with explicit truncation
  disclosures.
- Enforces configured per-collection/page/total-character limits.
- Materializes the task file outside the untrusted target checkout.

### 4. Existing solver reuse

- Reuses `solve_issue`, `LangGraphRuntime`, `Settings`, the workspace manager,
  repository tool layer, Docker sandbox, and authoritative `SolveResult`.
- Keeps deterministic orchestration outside prompts and model construction.
- Validates that the target checkout is a safe Git worktree at the exact gate
  base SHA before model configuration or runtime creation.
- Runs repository commands in the existing network-disabled sandbox without
  GitHub or OpenAI credentials.
- Preserves the local V0.1 CLI and artifacts as a supported compatibility path.

### 5. Deterministic publication

- Validates the solve workspace, local Git configuration, exact candidate HEAD,
  authoritative diff, authoritative changed paths, and `git diff --check` before
  publication.
- Uses the fixed branch `sage/issue-<number>` and refuses to overwrite a remote
  branch or duplicate open Pull Request.
- Fetches the current default branch and classifies it as unchanged or normally
  advanced; rewritten/non-ancestor history stops publication.
- Creates one deterministic commit with hooks and signing disabled and the
  explicit `Sage GitHub Actions` bot identity.
- Pushes only through an exact creation lease/refspec; it never pushes the
  default branch or force-updates an existing Sage branch.
- Supplies the token through a temporary external askpass helper rather than a
  credential-bearing URL, and removes that helper in `finally`.
- Creates a draft Pull Request containing `Closes #<issue>`, run/base metadata,
  authoritative paths, bounded summary, and bounded uncertainty.
- Preserves and reports an orphan branch if the push succeeds but PR creation
  cannot be reconciled.

### 6. Provenance and diagnostic artifacts

- Persists bounded `github.json` provenance alongside the existing authoritative
  solve artifacts.
- Copies only `metadata.json`, `github.json`, `agent-final.json`,
  `changed-files.json`, and `diff.patch` into the upload directory.
- Does not upload the checkout, `.git`, webhook payload, generated Issue context,
  `.env`, or an environment dump.
- Applies a seven-day diagnostic artifact retention in the workflow.

### 7. GitHub Actions controller

The repository owns two composite actions and one workflow:

- `.github/actions/sage-gate/action.yml` sets up locked Python dependencies and
  runs either the model-free gate or finalizer. It receives no model secret.
- `.github/actions/sage-solve/action.yml` checks out the exact recorded base
  with credentials disabled, builds the sandbox from pinned Sage source, and
  runs solve/publication with secrets scoped to the solve step.
- `.github/workflows/sage.yml` uses `issue_comment.created`, an empty top-level
  permission map, separate gate/solve/finalizer permissions, exact Issue-only
  filters, one concurrency group per Issue, `cancel-in-progress: false`, bounded
  job timeouts, immutable action pins, and allowlisted diagnostics.

External action revisions are full 40-character commits. The Sage workflow
references the immutable action implementation SHA shown at the top instead of
its own moving branch or the later workflow commit.

### 8. CLI and operator tooling

The CLI now exposes trusted workflow entry points:

```text
sage github gate
sage github solve
sage github finalize
sage github event-check
```

The root Makefile provides:

```text
make github-event-check EVENT=<fixture>
make github-test
make actions-check
make v1-check
make github-doctor
```

`github-event-check` is the safe offline parser/classifier. The other three CLI
entry points are internal controller operations and can mutate GitHub when given
real workflow credentials.

## Security properties retained

- Untrusted event and repository content is validated before use.
- A read-only commenter cannot reach the paid/model solve boundary.
- Gate and finalizer jobs do not receive the model secret.
- The target checkout does not retain GitHub checkout credentials.
- The sandbox receives no provider or GitHub credential and has no network.
- The publisher cannot push default, overwrite an existing Sage branch, or
  silently rebase an advanced default branch.
- Sage opens a draft only; it cannot auto-approve, auto-merge, or mark ready.
- The human commenter is the invoker, while the standard workflow token causes
  GitHub to attribute the commit/PR operation to `github-actions[bot]`.
- Logs, statuses, PR copy, Actions outputs, and uploaded artifacts are bounded
  and sanitized.

## Configuration and dependency changes

- Package version is `1.0.0`.
- Existing runtime dependencies are reused; no new production dependency was
  added.
- Exact `PyYAML==6.0.3` is a development-only dependency used to validate
  workflow/action manifests deterministically.
- `.env.example` documents the optional bounded GitHub controller settings:
  API timeout, comment count, comment pages, and total context characters.
- `SAGE_GITHUB_TOKEN`/`GITHUB_TOKEN` is not a committed setting. GitHub Actions
  supplies the job-scoped token at runtime.

## Verification contract

Run in this order from the repository root:

```bash
make setup
make v1-check
make sandbox-build
make sandbox-smoke
make github-doctor
```

The first command synchronizes the lock. `v1-check` runs the full Python suite,
byte compilation, focused GitHub tests, and action/workflow policy tests. The
Docker checks validate the same credential-free sandbox used by a live solve.
`github-doctor` verifies installed files/pins/documentation and Docker access
without printing secrets.

The deterministic suite uses fake GitHub/model boundaries and temporary Git
repositories. It does not prove that GitHub settings, organization policy,
repository secrets, hosted runners, or a live model call are correct. Those are
the purpose of the required canary.

Latest local verification on 2026-08-20:

  action/workflow policy tests, and byte compilation);
- `make github-event-check

- `make sandbox-smoke`: passed with Git, Python, and ripgrep in the
  network-disabled container; and
- `make github-doctor`: passed all installed-file, pin, guide, configuration,
  and Docker checks.

## Remaining rollout work

These are deployment/validation tasks, not missing application features:

1. Push or merge the action commit so
   `c24f1cf6fede2e69013b8229fe6c369cddefcf94` resolves on GitHub.
2. Push/merge the workflow and V1.0 release changes through normal review.
3. In a private throwaway/low-risk target, enable Actions and hosted runners,
   permit exact pinned actions and workflow PR creation, retain branch
   protection, and add the `OPENAI_API_KEY` Actions secret.
4. Execute and record every success, denial, duplicate, no-change, invalid-key,
   orphan, interruption, concurrency, artifact, and secret-audit scenario in
   testing-guide Section 15.
5. Resolve all failed security-boundary scenarios before enabling Sage in a
   production repository.

## Out of scope for V1.0

- Automatic merge, automatic approval, or automatic ready-for-review changes.
- Arbitrary user-selected branches or branch names.
- Personal access tokens or a separately deployed GitHub App service.
- Self-hosted runner support guarantees.
- Network access or credentials inside the repository sandbox.
- Database, queue, background polling, checkpoint persistence, or multi-agent
  orchestration.

These remain deliberate product boundaries rather than incomplete V1.0 tasks.
