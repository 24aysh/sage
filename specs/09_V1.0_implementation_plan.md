# Sage V1.0 GitHub-Native Implementation Plan

## Document status

This is the implementation-ready companion to
[`08_V1.0_design.md`](08_V1.0_design.md). It describes how to migrate the
working V0.1 local solver to V1.0 without replacing the proven LangGraph,
repository, artifact, or Docker execution core.

This document is a plan, not an as-built record. No V1.0 behavior should be
considered delivered until the implementation, deterministic checks, and live
GitHub acceptance scenarios listed here have passed.

The implementation target is Python 3.14, the version already required by the
backend. V1.0 must continue using the locked project environment rather than
introducing a second Python toolchain.

### Implementation progress

Part 1 was implemented in the working tree on 2026-08-19. It delivers the
foundation from Phases 0–2:

- shared trusted host-Git execution;
- shared atomic artifact writers with V0.1 compatibility coverage;
- exact Sage command parsing;
- pure write/admin authorization policy;
- bounded GitHub-only controller configuration;
- typed GitHub event models and `issue_comment.created` loading;
- repository/environment/SHA/URL/actor validation;
- sanitized Issue, alias, ordinary-comment, Pull Request, and malformed event
  fixtures;
- focused deterministic tests; and
- the user-facing [`10_V1.0_testing.md`](10_V1.0_testing.md) guide.

Part 2 was implemented in the working tree on 2026-08-19. It delivers Phase 3:

- a narrow GitHub client protocol and bounded standard-library REST transport;
- typed permission, Issue, comment, branch, and Pull Request responses;
- fixed-host API requests with component encoding and safe bounded errors;
- bounded GET/PATCH retry behavior and mutation-aware POST reconciliation;
- deterministic permission, open-PR, remote-branch, and status-marker checks;
- one create-or-reuse gate status comment per invocation;
- validated single-line GitHub Actions outputs;
- the internal, model-free `sage github gate` automation command;
- an offline `make github-test` developer command; and
- fake-transport/gate tests proving unauthorized and duplicate work cannot
  reach an accepted solve decision.

The issue-context builder, GitHub solve orchestration, publisher, terminal
statuses, composite actions, and enabled workflow remain intentionally
unimplemented at this boundary. A real `/sage solve` comment must not be
enabled until those later phases pass their tests and produce an immutable
action SHA.

## 1. Intended outcome

V1.0 adds a GitHub-native controller around the existing local solve workflow:

```text
authorized issue comment
        │
        │ /sage solve or /sage fix
        ▼
GitHub Actions command gate
        │
        ├── reject ordinary/PR comments
        ├── verify actor permission
        ├── serialize the issue
        └── reject an existing Sage branch/PR
        ▼
GitHub Actions solve job
        │
        ├── check out the exact event base commit
        ├── render bounded issue context
        ├── call the existing solve_issue workflow
        ├── run the existing LangGraph agent in Docker
        └── derive the result from Git
        ▼
trusted host-side publisher
        │
        ├── create a deterministic Sage branch
        ├── commit the candidate
        ├── push only the Sage branch
        └── open a draft Pull Request
        ▼
issue status comment with the Pull Request link
```

The migration is additive. The existing command remains supported:

```bash
sage solve --repo /path/to/repo --issue-file /path/to/issue.md
```

Its arguments, exit codes, sandbox behavior, result calculation, and V0.1
artifact files must remain compatible.

## 2. Locked implementation decisions

The following decisions remove ambiguity before coding begins.

1. V1.0 uses the `issue_comment` `created` event. Edited or deleted comments do
   not invoke Sage.
2. A supported command is a complete, case-sensitive comment body equal to
   `/sage solve` or `/sage fix`. Leading/trailing whitespace, surrounding text,
   Markdown code blocks, and different casing are not accepted.
3. Only comments on GitHub Issues are eligible. Comments on Pull Requests are
   ignored even though GitHub delivers both through `issue_comment`.
4. The actor must have GitHub's calculated `write` or `admin` repository
   permission. GitHub maps `maintain` to the legacy `write` permission. `read`,
   `triage`, `none`, and permission lookup failures do not authorize a paid
   run.
5. Authorization and duplicate detection happen in a job that does not receive
   `OPENAI_API_KEY`. The solve job repeats the checks immediately before it
   constructs the model runtime.
6. The exact base is the default-branch commit exposed as `GITHUB_SHA` for the
   accepted `issue_comment` event. The branch name comes from the event's
   repository object. Both are validated and recorded.
7. V1.0 uses the existing `SolveRequest`, `solve_issue`, `LangGraphRuntime`,
   `RepositoryTools`, `DockerSandbox`, and `ArtifactStore`. GitHub issue context
   is materialized as a temporary issue file so the core workflow does not gain
   provider-specific behavior.
8. The deterministic branch name is `sage/issue-<issue-number>`. The model
   cannot select the branch, base, remote, commit message, or PR destination.
9. The publisher opens a draft Pull Request. Sage never pushes the default
   branch, force-overwrites an existing branch, auto-merges, or marks its own PR
   ready for review.
10. GitHub integration uses a small project-owned REST client built with the
    Python standard library. V1.0 does not add PyGithub, Octokit, `gh` as a
    runtime dependency, a GitHub App, a PAT, a database, or a service process.
11. Target repositories install a thin workflow that invokes Sage's gate and
    solve composite actions at a full immutable commit SHA. Tags and moving
    branches are not accepted in the production installation example.
12. GitHub.com is the supported V1.0 deployment. GitHub Enterprise Server
    compatibility is deferred until its API, runner, and URL trust rules are
    designed and tested explicitly.

## 3. Current V0.1 baseline and reuse map

The implementation must extend existing ownership rather than reimplementing
the solver.

| Existing responsibility | Current implementation | V1.0 use |
| --- | --- | --- |
| Local solve request | `sage.domain.requests.SolveRequest` | Construct with the checked-out repository, generated issue file, and exact SHA. |
| Isolated run checkout | `sage.repository.workspace.prepare_run` | Reuse unchanged; its second local clone keeps each solve independent. |
| Solve lifecycle | `sage.workflow.solve_issue` | Reuse as the only coding workflow entrypoint. |
| Agent boundary | `sage.domain.runtime.AgentRuntime` | Keep provider-neutral and GitHub-independent. |
| Agent runtime | `sage.runtimes.langgraph.LangGraphRuntime` | Reuse without changing graph topology or tool routing. |
| Repository operations | `sage.repository.RepositoryTools` | Reuse all six bounded tools. |
| Sandbox | `sage.sandbox.docker.DockerSandbox` | Reuse the current network-disabled and credential-free container. |
| Authoritative result | `sage.domain.results.SolveResult` | Use Git-derived changed files and complete diff for publication. |
| Local artifacts | `sage.artifacts.ArtifactStore` | Preserve existing files; add separate GitHub provenance only for GitHub runs. |
| Controller settings | `sage.config.Settings` | Preserve all existing variables and load them only in the authorized solve path. |
| Errors | `sage.errors.SageError` hierarchy | Extend with focused GitHub event, API, and publishing errors. |
| Local CLI | `sage.cli` | Retain `sage solve`; add a nested automation-only `sage github` command group. |
| Developer commands | root `Makefile` | Extend the existing toolchain; do not create a parallel script runner. |

The following V0.1 behavior is specifically not part of this migration:

- the graph remains a single-agent `sage_v0_1` graph;
- the six repository tool contracts do not change;
- the model still receives no GitHub credential;
- Git remains authoritative over model-provided changed-file claims;
- normal unit tests require no live model call;
- local CLI exit code `0`, `1`, and `2` meanings remain unchanged; and
- the existing run artifact names remain valid for local users.

## 4. Delivery and installation model

### 4.1 Repository installation

V1.0 does not require an always-running Sage service. A target repository is
enabled once by adding a small workflow based on the checked-in installation
template. That workflow:

- listens for `issue_comment` events;
- grants explicit job-level permissions;
- supplies the repository's `GITHUB_TOKEN`;
- supplies `OPENAI_API_KEY` only to the solve action;
- invokes both Sage actions from `24aysh/sage` at the same full commit SHA; and
- sets concurrency and job timeout limits.

The maintainer then interacts only through issue comments. They do not clone
the repository, create an issue file, build Docker locally, or run a CLI for
each issue.

### 4.2 Sage action packaging

Add two composite actions:

```text
.github/actions/sage-gate/action.yml
.github/actions/sage-solve/action.yml
```

They are separate because GitHub permissions and secret access are job-scoped:

- `sage-gate` installs only the trusted controller, parses the event, checks
  permission and duplicate state, and creates/reuses the issue status comment;
- `sage-solve` checks out the target revision, prepares the sandbox, runs the
  existing solver, publishes the candidate, and updates the issue status.

The composite actions must resolve the controller root from
`github.action_path`. They must never assume that the target repository itself
contains Sage. The target checkout lives under a dedicated path such as
`$GITHUB_WORKSPACE/target`, while the downloaded action remains the trusted
controller source.

### 4.3 Immutable release sequencing

An enabled workflow cannot securely point to the same not-yet-created commit
that contains it. Rollout therefore uses two logical steps:

1. land and verify the Python integration plus composite actions;
2. enable the repository workflow in a later commit, pinning both actions to
   the full SHA produced by step 1.

The V1.0 testing guide must contain the concrete tested SHA. A release update
must deliberately bump that pin; a tag alone is insufficient for the
production example.

## 5. Target architecture and ownership

```text
GitHub event and APIs
        │
        ▼
sage.integrations.github
  event parsing, authorization, API transport,
  context rendering, statuses, publication
        │
        ▼
sage.workflow.github_issue
  provider-specific lifecycle coordination
        │
        ▼
existing sage.workflow.solve_issue
        │
        ├── existing LangGraph runtime on trusted host
        ├── existing isolated run clone
        └── existing Docker repository tools
```

The planned source layout is:

```text
apps/agent/src/sage/
  integrations/
    __init__.py
    github/
      __init__.py
      authorization.py
      client.py
      commands.py
      config.py
      context.py
      events.py
      models.py
      publishing.py
      status.py
  repository/
    host_git.py
  workflow/

```

Focused tests mirror those boundaries:

```text
apps/agent/tests/
  fixtures/github/
  integrations/github/
    test_authorization.py
    test_client.py
    test_commands.py
    test_config.py
    test_context.py
    test_events.py
    test_publishing.py
    test_status.py
  repository/test_host_git.py
  workflow/test_github_issue.py
```

Responsibilities must not drift:

- event parsing validates GitHub data but performs no network calls;
- authorization maps a calculated permission to a decision;
- the REST client performs HTTP and validates provider responses;
- context rendering is deterministic and does not call the model;
- publication owns host-side Git and PR creation only;
- the GitHub workflow coordinates those services and the existing solver;
- the LangGraph runtime remains unaware of events, comments, branches, and PRs;
- repository tools never receive GitHub or model credentials.

## 6. Trust boundary

### 6.1 Trusted controller

The GitHub-hosted runner may hold:

- the Sage action pinned to an immutable commit;
- `GITHUB_TOKEN` with the current job's explicit permissions;
- `OPENAI_API_KEY` in the authorized solve job only;
- LangGraph and model integration code;
- deterministic Git publication code; and
- temporary run metadata.

### 6.2 Untrusted inputs

The following are untrusted even when the invoker is authorized:

- issue title and body;
- every issue comment and username;
- repository names and branch names read from event data;
- target repository files and Git metadata;
- repository instructions and source comments;
- sandbox command output;
- model-generated summaries and uncertainty; and
- Git file paths rendered back into Markdown.

Untrusted values must be parsed as data. They must not be interpolated directly
into a `run:` shell program, a Git refspec, a URL host, a credential location,
or a workflow expression that grants authority.

### 6.3 Disposable repository execution

Only the existing Docker sandbox may execute target repository commands. The
host may use Git for checkout, status, diff, commit, fetch, and push, but it may
not run target build scripts, hooks, package managers, or tests.

The sandbox remains:

- network-disabled;
- non-privileged;
- without the Docker socket;
- without model or GitHub credentials;
- limited to the isolated candidate workspace mount;
- bounded by CPU, memory, process, and command timeout controls; and
- removed through the existing `finally` cleanup path.

## 7. Data contracts

### 7.1 Command model

Define an enum with one semantic action and two accepted spellings:

```text
/sage solve ─┐
             ├── SageCommand.SOLVE
/sage fix ───┘
```

`parse_command(body: str) -> SageCommand | None` must be pure. It returns
`None` for all unsupported input rather than attempting fuzzy interpretation.

### 7.2 Invocation model

A frozen Pydantic model should contain only the validated event subset needed
by the controller:

- repository owner, name, numeric ID, and HTML URL;
- issue number, title, body, and HTML URL;
- actor login and numeric ID;
- invoking comment ID, body, creation time, and HTML URL;
- parsed command;
- repository default branch;
- exact event base SHA;
- Actions run ID, attempt, and URL; and
- whether the event object represents a Pull Request.

The model must not retain the full webhook payload. Validation must reject:

- any action other than `created`;
- a missing or malformed repository identity;
- a non-positive issue/comment/run identifier;
- an empty actor;
- an invalid commit SHA;
- an absent default branch; and
- a repository whose `full_name` does not match its owner/name fields.

The initial implementation may accept 40- or 64-character lowercase
hexadecimal object IDs so it does not bake shell behavior around one hash
length. The exact SHA is always passed to Git as an argument after validation.

### 7.3 API response models

Use small frozen models for:

- calculated repository permission;
- issue snapshot;
- issue comment;
- branch snapshot;
- issue status comment;
- open Pull Request; and
- created Pull Request.

Models should ignore unknown GitHub response fields but require every field the
controller uses. Do not spread raw dictionaries through orchestration code.

### 7.4 Outcomes

The GitHub workflow should return a typed outcome with one of:

- `pull_request_created`;
- `no_changes`;
- `existing_pull_request`;
- `unauthorized`;
- `ignored`;
- `blocked_existing_branch`; or
- `failed`.

Expected gate decisions are outcomes, not exceptions. Malformed events,
unreachable APIs, invalid provider responses, solve failures, and publication
failures use focused exceptions rooted at `SageError`.

## 8. Configuration contract

Keep GitHub configuration in `sage.integrations.github.config` so the gate can
load its settings without requiring the model key.

| Value | Source/default | Loaded by |
| --- | --- | --- |
| GitHub token | required action input exposed only as `SAGE_GITHUB_TOKEN` to trusted steps | gate and solve controller |
| Event path | `GITHUB_EVENT_PATH` | event parser |
| Exact base | `GITHUB_SHA` | event parser |
| Run metadata | `GITHUB_RUN_ID`, `GITHUB_RUN_ATTEMPT`, `GITHUB_SERVER_URL`, `GITHUB_REPOSITORY` | event parser |
| API URL | fixed `https://api.github.com` for V1.0 | REST client |
| API timeout | `SAGE_GITHUB_API_TIMEOUT_SECONDS`, default `30` | REST client |
| Maximum context comments | `SAGE_GITHUB_MAX_COMMENTS`, default `20` | context builder |
| Maximum comment pages | `SAGE_GITHUB_MAX_COMMENT_PAGES`, default `5` | context builder |
| Maximum task context | `SAGE_GITHUB_MAX_CONTEXT_CHARS`, default `40000` | context builder |
| OpenAI key/model | existing `OPENAI_API_KEY`, `OPENAI_MODEL` | authorized solve only |
| Agent/sandbox limits | existing `SAGE_*` settings | existing solver |
| Run directory | action sets `SAGE_RUNS_DIR` below `$RUNNER_TEMP` | existing solver |
| Sandbox image | existing `SAGE_SANDBOX_IMAGE` default | action build and solver |

All numeric GitHub settings require bounded Pydantic validation. Tokens use
`repr=False`, never appear in validation errors, and are never added to a model
that is serialized as an artifact.

`.env.example` should document only values relevant to local development. It
must not encourage committing `GITHUB_TOKEN`; GitHub supplies that token at job
runtime.

## 9. Event and command gate

### 9.1 Workflow-level filter

The enabled workflow uses:

```yaml
on:
  issue_comment:
    types: [created]
```

Its gate job has an `if` expression that requires:

- the issue object not to contain `pull_request`; and
- the entire body to equal `/sage solve` or `/sage fix`.

This avoids allocating a runner for ordinary comments or PR conversation. The
Python parser repeats the rule because workflow YAML is not the application
security boundary.

### 9.2 Gate sequence

The gate action performs these operations in order:

1. parse and validate the event file and trusted Actions environment;
2. reject any mismatch between the event repository and `GITHUB_REPOSITORY`;
3. parse the exact command;
4. request the actor's calculated repository permission;
5. deny `read`, `none`, and missing actors without exposing a model secret;
6. derive `sage/issue-<number>` from the validated numeric issue number;
7. query for an open PR whose head is that branch;
8. query whether that remote branch already exists;
9. find a prior status comment for the same invoking comment ID;
10. create or update one accepted status comment; and
11. emit only validated, non-secret outputs required by the solve job.

Outputs are:

- `should_run`, exactly `true` or `false`;
- `base_sha`;
- `base_branch`;
- `status_comment_id`;
- `issue_number`; and
- `existing_pr_url`, empty when no existing PR was found.

The output writer must use the file named by `GITHUB_OUTPUT`. Values must be
validated single-line values before writing. No issue text or model/provider
value belongs in job outputs.

### 9.3 Authorization policy

Use `GET /repos/{owner}/{repo}/collaborators/{username}/permission` and inspect
the calculated legacy `permission` field:

| GitHub permission | Gate result |
| --- | --- |
| `admin` | authorized |
| `write` (including maintain) | authorized |
| `read` (including triage) | denied |
| `none` | denied |
| `404` | denied |
| malformed/`403`/network failure | configuration or API failure; no model call |

Do not use `author_association` as the authority. It does not represent the
current effective permission from repository, team, organization, and
enterprise grants.

### 9.4 Duplicate policy

V1.0 has one active Sage branch per issue:

- if an open PR already uses `sage/issue-<number>`, skip the solve and link it;
- if the branch exists without an open PR, do not overwrite it and give manual
  recovery instructions;
- if neither exists, the invocation may proceed;
- after a closed or merged PR, a new invocation is allowed only when the remote
  branch no longer exists; and
- a workflow re-run for the same invoking comment reuses its status comment by
  hidden marker rather than creating a second one.

This policy permits deliberate later attempts while preventing concurrent
paid runs and branch overwrites.

## 10. Workflow concurrency

GitHub concurrency must serialize only supported commands for the same issue.
Ordinary and PR comments must use a unique comment-based group so they cannot
delay or replace a Sage invocation.

The group is conceptually:

```text
supported issue command:
  sage-<repository-id>-issue-<issue-number>

all other comments:
  sage-<repository-id>-comment-<comment-id>
```

Set `cancel-in-progress: false`. This lets the active issue solve finish. Under
GitHub's default single-pending behavior, a newer repeated command may replace
an older still-pending command, but it cannot cancel the paid run in progress.
Because the pending workflow has not entered the gate, no stale accepted
comment is left behind. When the remaining command starts, duplicate checks run
again.

Concurrency is not the only defense. The solve job repeats authorization and
branch/PR checks, and publication uses a creation-only branch update so a race
cannot overwrite an existing ref.

## 11. GitHub Actions jobs and permissions

The workflow starts with `permissions: {}` and grants only job-specific access.

| Job | Permissions | Secrets | Timeout | Purpose |
| --- | --- | --- | --- | --- |
| `gate` | `contents: read`, `issues: write`, `pull-requests: read` | repository `GITHUB_TOKEN` only | 10 minutes | Validate, authorize, deduplicate, create status. |
| `solve` | `contents: write`, `issues: write`, `pull-requests: write` | `GITHUB_TOKEN`, `OPENAI_API_KEY` | 90 minutes | Checkout, solve, publish, report. |
| `finalize` | `issues: write`, `pull-requests: read` | repository `GITHUB_TOKEN` only | 5 minutes | Repair a non-terminal status after setup, cancellation, or controller failure. |

The solve job runs only when `gate.should_run == 'true'`. It must:

1. check out the target repository at `gate.base_sha`, not a moving branch;
2. set `persist-credentials: false` and fetch enough history to preserve the
   exact base and support base ancestry checks;
3. set up Python 3.14 and the locked `uv` environment from the Sage action;
4. build the existing Docker sandbox image from the pinned Sage source;
5. set run and context directories below `$RUNNER_TEMP`;
6. execute the internal GitHub solve command; and
7. upload only whitelisted diagnostic artifacts with short retention.

Every external action, including checkout, Python/uv setup, artifact upload,
and fallback status handling, must be pinned to a verified full commit SHA with
a nearby version comment.

## 12. GitHub REST client

### 12.1 Boundary

Define a narrow `GitHubClient` protocol for orchestration tests and a
`RestGitHubClient` implementation using `urllib.request`, `json`, and
`urllib.parse`. No other module builds API URLs or authorization headers.

Every request includes:

- `Authorization: Bearer <token>`;
- `Accept: application/vnd.github+json`;
- `X-GitHub-Api-Version: 2026-03-10`;
- a bounded timeout; and
- a Sage-specific `User-Agent`.

Repository, user, branch, and query components are percent-encoded by component.
The host is fixed by configuration and is never derived from issue text.

### 12.2 Required endpoints

| Operation | REST endpoint |
| --- | --- |
| Effective actor permission | `GET /repos/{owner}/{repo}/collaborators/{actor}/permission` |
| Current issue | `GET /repos/{owner}/{repo}/issues/{number}` |
| Issue comments | `GET /repos/{owner}/{repo}/issues/{number}/comments` |
| Create status | `POST /repos/{owner}/{repo}/issues/{number}/comments` |
| Update status | `PATCH /repos/{owner}/{repo}/issues/comments/{comment_id}` |
| Inspect branch | `GET /repos/{owner}/{repo}/branches/{branch}` |
| Find open Sage PR | `GET /repos/{owner}/{repo}/pulls?state=open&head={owner}:{branch}&base={base}` |
| Open draft PR | `POST /repos/{owner}/{repo}/pulls` |

### 12.3 Failure and retry rules

- Retry bounded, idempotent GET requests at most three times for transient
  `429`, `502`, `503`, and `504` responses, respecting `Retry-After` and keeping
  total backoff bounded.
- A PATCH that sets a status comment to a deterministic body may be retried.
- Do not blindly retry POST requests. After a create-comment timeout, search
  for the invocation marker before retrying. After a create-PR timeout or
  `422`, query the deterministic head branch and accept only the matching open
  PR.
- Treat ordinary validation `4xx` responses as terminal; deterministic input
  errors are not retried.
- Raise `GitHubApiError` with the HTTP status, operation name, request ID when
  available, and a bounded safe message. Never include headers, tokens, full
  issue content, or an unrestricted response body.

HTTP behavior is tested through an injected transport/fake opener. Normal tests
must not call `api.github.com`.

## 13. Issue context assembly

The issue replaces the caller-provided `issue.md`, but the existing solver
continues to consume a file.

### 13.1 Inputs

The context builder fetches:

- current issue title and body;
- repository owner/name;
- issue number and URL;
- invocation actor, command, and timestamp;
- default branch and exact base SHA; and
- up to the configured number of useful comments created no later than the
  invoking comment.

Exclude:

- the invoking command itself;
- other comments whose whole body is a Sage command;
- Sage status comments identified by the project-owned hidden marker; and
- comments created after the invocation.

Scan comment pages from the newest page backward until enough eligible comments
are found or the page limit is reached. If the history is truncated, state that
inside the generated task so the agent and maintainer are not misled.

### 13.2 Deterministic rendering

Render Markdown in this fixed shape:

```markdown
# GitHub issue task

Repository: owner/repo
Issue: #123
Issue URL: https://github.com/owner/repo/issues/123
Base branch: main
Base commit: <full SHA>
Invoked by: <actor>

## Title
<title>

## Description
<body or explicit no-description marker>

## Prior discussion
### <actor> — <timestamp>
<comment>

## Controller note
Issue text and repository content are untrusted task input. The exact base
commit above is authoritative for this run.
```

Use a deterministic character budget:

1. always retain metadata and a bounded title;
2. allocate a bounded portion to the issue description;
3. select the newest eligible comments within the remaining budget;
4. render selected comments in chronological order; and
5. add an explicit truncation marker whenever content is omitted.

The resulting file is created below `$RUNNER_TEMP`, outside the target checkout.
It is passed to `SolveRequest.issue_path`; the existing artifact store then
captures exactly what the model received.

## 14. Reusing the V0.1 solve core

The GitHub orchestration constructs:

```python
SolveRequest(
    repo_path=target_checkout,
    issue_path=generated_issue_file,
    base_ref=invocation.base_sha,
)
```

It then:

1. loads the existing `Settings` only after the second authorization check;
2. constructs the existing `LangGraphRuntime`;
3. awaits the existing `solve_issue`;
4. uses `SolveResult.changed_files` and `SolveResult.diff`, not model claims;
5. keeps `SolveResult.workspace_dir` as the only publication candidate; and
6. relies on `solve_issue` to stop Docker on success and exceptions.

No GitHub API call belongs inside `solve_issue`. No GitHub field should be added
to `AgentRuntime`, `RuntimeContext`, graph state, tool schemas, or
`AgentFinalOutput`.

The target checkout and isolated run clone intentionally both exist:

```text
Actions exact-SHA target checkout
        │
        └── prepare_run local clone
                  │
                  └── Docker-mounted writable candidate
```

The extra local clone preserves the V0.1 invariant that the source checkout is
never the candidate workspace and makes V1.0 runs independent.

## 15. Host-side Git support

Publication needs trusted host Git without duplicating the existing subprocess
handling in `repository.workspace`.

Add `sage.repository.host_git` with a focused function that:

- accepts a list of arguments rather than a shell string;
- accepts an explicit repository path, timeout, and optional environment;
- captures text output;
- maps missing Git and timeouts to focused Sage errors;
- does not log environment values; and
- returns enough structured output for workspace preparation and publication.

Refactor `prepare_run` to use this helper without changing its behavior or
messages. The publisher then reuses the same executor. This refactor and its
tests should land before GitHub publishing so its compatibility can be reviewed
independently.

## 16. Publication policy

### 16.1 Pre-publication validation

If `SolveResult.diff` is empty, do not create a branch, commit, or PR. Update the
issue status to `completed: no repository changes` and retain the agent summary
and uncertainty in bounded form.

For a non-empty result, the publisher must verify:

- the candidate HEAD still equals `SolveResult.base_sha` before staging;
- `git diff --check` succeeds;
- staged changed files equal the authoritative `SolveResult.changed_files`;
- the deterministic branch name is valid and is not the base branch;
- no open matching PR or remote branch appeared since the gate; and
- the remote URL is derived from the validated event repository on
  `https://github.com`, not from candidate Git config or model output.

### 16.2 Base movement

Immediately before publishing, fetch the current default branch into a
controller-owned remote-tracking ref and compare it to the recorded event SHA.

- If unchanged, publish normally.
- If the current base is a descendant of the event SHA, do not rebase. Publish
  the original candidate and add both SHAs plus a visible base-advanced warning
  to the PR body.
- If the event SHA is no longer an ancestor of the default branch, treat the
  base as rewritten, do not push a candidate, and ask the maintainer to retry.

The PR always targets the named current default branch. Sage never silently
changes the code after the agent has inspected and tested it.

### 16.3 Commit and push

Use this deterministic sequence:

1. create local branch `sage/issue-<number>` from the detached exact base;
2. set repository-local bot name/email and disable commit signing;
3. stage with `git add --all -- .`;
4. verify staged paths and `git diff --cached --check`;
5. commit with fixed message `fix: resolve issue #<number>` and `--no-verify`;
6. recheck that the remote branch is absent;
7. push `HEAD` only to `refs/heads/sage/issue-<number>` with a
   creation-only lease that expects the remote ref not to exist; and
8. never use a general force push or a default-branch refspec.

The creation-only lease is a race-safety check, not permission to replace a
branch. Tests must assert that an existing remote ref is never updated.

### 16.4 Git credential handling

The target checkout uses `persist-credentials: false`. For fetch/push, create a
temporary `GIT_ASKPASS` program below `$RUNNER_TEMP` that reads the token only
from the trusted subprocess environment.

The token must not appear in:

- a remote URL;
- `.git/config`;
- command arguments;
- the askpass file itself;
- captured error text;
- logs; or
- artifacts.

Set `GIT_TERMINAL_PROMPT=0`, scope the token environment to the individual Git
subprocess, and remove the askpass file in `finally` on success and failure.

### 16.5 Pull Request

After a successful push, create a draft PR with:

- base: validated default branch;
- head: deterministic Sage branch;
- title: `Sage: <bounded, single-line issue title>`;
- a generated-by-Sage notice;
- `Closes #<issue-number>`;
- concise agent summary;
- authoritative changed-file list;
- remaining uncertainty;
- original base SHA and current base SHA;
- Actions run URL; and
- a hidden stable Sage marker.

Model output and issue text are sanitized before Markdown rendering: control
characters and injected hidden markers are neutralized, user mentions are made
non-notifying, and every section has a length/item bound.

If branch push succeeds but PR creation fails, do not delete or overwrite the
branch automatically. Mark the issue failed with the branch URL and recovery
guidance. A later gate will detect the orphan branch and avoid another paid run
until a maintainer creates the PR or deletes the branch deliberately.

## 17. Issue status state machine

Use one project-owned status comment per invocation. Its hidden marker is based
only on the validated command comment ID:

```html
<!-- sage-invocation:<comment-id> -->
```

Include a second machine-readable state marker so fallback handling can detect
terminal states without parsing human text.

```text
accepted
    │
    ▼
working
    ├── pull_request_created
    ├── no_changes
    └── failed
```

Status bodies include the Actions run link. Human-facing text remains concise:

- **accepted** — actor authorized; run queued against a short base SHA;
- **working** — isolated solve started;
- **pull request created** — link to draft PR and short summary;
- **no changes** — completion without a branch, plus uncertainty/retry advice;
- **failed** — safe category, run link, and actionable recovery text.

Unauthorized commands receive a separate concise denial response and never an
accepted state. Ordinary comments and PR comments receive no response.

The `finalize` job runs with `always()` after gate/solve. It fetches the status
comment and changes it to a generic failed state only if no trusted terminal
state marker exists. This covers setup failure, Docker build failure, hard job
failure, and controller termination without overwriting a more useful failure
already published by Python.

## 19. Failure behavior

| Failure | Required behavior |
| --- | --- |
| Ordinary or PR comment | No runner work beyond GitHub's event filter; no response. |
| Unauthorized actor | No model key/job; concise denial response. |
| Permission API unavailable | Gate fails; no solve job; safe setup failure response/log. |
| Existing open Sage PR | No model call; status links the existing PR. |
| Existing orphan branch | No model call; recovery guidance; no overwrite. |
| Target checkout failure | No model call; generic finalizer status. |
| Docker image build/start failure | No agent result or branch; cleanup attempt and failed status. |
| Model/graph/tool-limit failure | Existing sandbox cleanup; no commit/push; failed status. |
| Agent returns no diff | Successful no-change status; no branch or PR. |
| Diff validation/commit failure | No push; failed status. |
| Default branch rewritten | No push; retry guidance. |
| Branch race/push rejection | No PR; no overwrite; failed status. |
| PR API failure after push | Preserve branch; failed status includes branch recovery. |
| Issue status update failure after PR | Preserve PR; Actions logs identify status failure; finalizer reconciles when possible. |
| Job cancellation/timeout | Hosted runner is discarded; finalizer updates status if scheduled. No persistent container or credentials remain. |

Errors shown on the issue identify the category and run URL, not a Python type,
stack trace, provider payload, or sensitive command output.

## 20. Security controls

Implementation review must verify all of the following:

- exact command parsing occurs in YAML and Python;
- the event is an Issue, not a Pull Request;
- effective permission is checked before model execution and rechecked in solve;
- workflow top-level permissions are empty and jobs are least-privileged;
- `OPENAI_API_KEY` is absent from gate/finalize jobs;
- target code never runs on the trusted host;
- target commands run only in the network-disabled Docker sandbox;
- no model or GitHub credential enters Docker arguments, environment, or mount;
- the Docker socket is never mounted;
- untrusted event values are not embedded in shell source;
- all subprocesses use argument lists except existing sandbox commands, which
  execute inside the untrusted boundary;
- publication refs and URLs are controller-derived and validated;
- checkout credentials are not persisted;
- the publisher does not run Git hooks;
- Git credentials are temporary and cleaned up;
- branches are creation-only and default-branch pushes are structurally
  impossible;
- PR creation is draft-only and there is no merge API call;
- status/PR Markdown neutralizes hidden-marker and mention injection;
- external actions and Sage itself are pinned to full commit SHAs;
- HTTP retries are bounded and mutation-aware; and
- artifacts are allowlisted rather than recursively uploaded.

Do not use `pull_request_target`. Do not use an issue's `author_association` as
authorization. Do not expose a repository-controlled script as a trusted host
step.

## 23. Test plan

### 23.1 Pure unit tests

Command tests cover:

- both exact aliases;
- uppercase/lowercase variations;
- leading/trailing whitespace;
- explanatory text before/after command;
- quoted commands and fenced code blocks;
- empty/Unicode/control-character input; and
- Sage-generated status bodies.

Event tests cover:

- a valid issue event;
- a PR conversation event;
- actions other than `created`;
- repository/environment mismatches;
- invalid IDs, SHA, URLs, and dates;
- missing actor/comment/issue fields; and
- payload additions that should be ignored safely.

Authorization tests cover every permission result and API error category.

Context tests cover:

- issue with/without body;
- comments before and after invocation;
- command/status exclusion;
- newest-comment selection and chronological rendering;
- per-section and total truncation;
- Markdown/control/hidden-marker content; and
- page-limit truncation disclosure.

Status tests cover every transition, stable markers, output bounds, mention
neutralization, and terminal-state detection.

### 23.2 REST client tests

Using a fake transport, assert:

- method, path/query encoding, headers, API version, and timeout;
- response model validation;
- pagination link handling and limits;
- 404 permission/branch behavior;
- bounded GET retry and `Retry-After` handling;
- comment and PR POST reconciliation;
- safe 4xx/5xx messages; and
- tokens and issue bodies never appear in exceptions/log records.

### 23.3 Publisher tests

Use temporary Git repositories and a local bare remote to test:

- no-diff short circuit;
- branch and commit identity/message;
- staged file list matching;
- untracked, deleted, renamed, and binary changes;
- `diff --check` failure;
- unchanged, advanced, and rewritten base;
- exact pushed ref;
- rejection when branch exists;
- inability to push the default branch;
- askpass removal on success, subprocess failure, and API failure;
- PR payload bounds and sanitization;
- PR idempotency after an ambiguous API response; and
- orphan-branch reporting when PR creation fails.

No test should place a real token in a process or remote URL. Use sentinel
values and assert they do not appear in output.

### 23.4 Workflow orchestration tests

With fake API/runtime/publisher boundaries, cover:

- unauthorized invocation never constructs a runtime;
- duplicate PR and orphan branch never construct a runtime;
- permission revoked between gate and solve;
- context passed to the existing solver at exact SHA;
- successful publish and final issue link;
- no-change completion;
- agent, sandbox, artifact, publisher, and status failures;
- Docker cleanup delegated through `solve_issue`; and
- GitHub provenance without secrets.

### 23.5 Compatibility tests

- Run every existing backend test unchanged.
- Keep local CLI parser, prerequisite, result, and exit-code tests.
- Keep exact V0.1 artifact-file tests.
- Keep LangGraph node/route/tool/runtime tests.
- Keep Docker command tests proving no credential environment is added.

### 23.6 Workflow and security tests

Static validation must assert:

- event type is only `issue_comment.created`;
- PR comments and non-command comments are filtered;
- top-level permissions are empty;
- gate has no model secret;
- solve uses explicit minimal write permissions;
- exact-SHA checkout and `persist-credentials: false` are present;
- every `uses:` reference is a full commit SHA or a checked-in local action
  used only by development tests;
- concurrency does not cancel the active solve;
- solve/finalize timeouts are bounded;
- no `pull_request_target`, direct default push, or merge operation exists; and
- artifact paths are allowlisted.

### 23.7 Live acceptance tests

Run in a private or throwaway repository with Actions PR creation enabled:

1. ordinary issue comment — no Sage response or model run;
2. `/sage solve` on a PR — ignored;
3. command from read-only user — denied before model execution;
4. command from write user — accepted and working status appears;
5. successful fixture — draft PR from `sage/issue-N`, correct commit and issue
   link, default branch unchanged;
6. `/sage fix` — same behavior as solve;
7. repeated command during run — no second concurrent paid run;
8. repeated command with open PR — existing PR linked, no model run;
9. no-change fixture — terminal issue status, no branch/PR;
10. forced model/config failure — concise issue failure, no branch, no container;
11. PR API failure simulation — orphan branch reported, later invocation blocked;
12. two different issues — independent workspaces/containers/branches; and
13. artifact/log review — no provider/GitHub credential or raw environment.

Paid live model calls are limited to this controlled acceptance suite and are
never part of `make test`.

## 27. Known platform behavior and limitation

GitHub's current `GITHUB_TOKEN` behavior prevents most token-created events
from recursively creating workflows. A Pull Request opened or updated by a
workflow can create `pull_request` runs in an approval-required state. V1.0
accepts that maintainer approval step rather than adding a PAT or GitHub App,
which are explicit non-goals.

Therefore:

- Sage should run relevant repository tests inside its sandbox before it
  finishes when the issue requires them;
- the draft PR may show checks waiting for a maintainer to approve their runs;
- documentation must explain that state clearly; and
- V1.0 must not weaken repository workflow approval rules to make checks appear
  automatically green.

## 29. Logical commit plan

When the user authorizes commits, use signed Conventional Commits and keep
implementation tests with the behavior they verify. A reasonable split is:

1. `refactor(repository): share trusted host git execution`
2. `refactor(artifacts): share atomic artifact writers`
3. `feat(github): add command event and authorization gate`
4. `feat(github): add issue context and workflow orchestration`
5. `feat(github): publish solved candidates as draft pull requests`
6. `feat(actions): add pinned Sage gate and solve actions`
7. `ci(actions): enable authorized issue solve workflow`
8. `docs: add V1 setup and manual testing guide`

The exact count may shrink if a boundary is too small to stand alone, but these
concerns should not be collapsed into one broad commit. The enabled workflow
must remain later than the commit it pins.
